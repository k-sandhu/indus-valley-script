# Protocol: face-level image index and dimension units audit, 13 October 2026

Written before the index, the dimension table or any coverage figure was computed. Before writing it I profiled the shapes of the file names and of the dimension strings, read the CISI 1 introduction on side letters and photograph labels (printed pp. XXIV–XXV, PDF 28–29, renders made by the plate-check package), viewed eight crops with unusual names, and confirmed that tesseract 5.4 reads the CISI 1 page headings. Package of data round 1; question cards Q-1004 and Q-1020. It tests no hypothesis about the script.

## Questions

1. For every face in `data/normalized/lipi_observed_faces.jsonl`, which local image files show it, as a photograph of the object or of a modern impression, of which side, from which CISI volume and page, and which faces have no image? How much does object and face coverage change against the data inventory's rule (raw CISI key in the Lipi index with an existing file, 53.4% of objects)?
2. For every local dimension value, what source holds it, in what unit and to what precision was it recorded, is the millimetre value a conversion, and where do the local sources disagree? How many seals in each half of the October 12 split carry rounded or converted sizes?

## Inputs

All local and hash-recorded in the run directory: the Lipi faces file (SHA-256 `1220f559…`), the 8,722 files in `data/lipi/public/seal_images/`, the Lipi index `seal_id_and_image_mapping.json`, the Lipi `inscriptions.csv`, the older website export `data/normalized/indus_website_observed.jsonl` and its SQL `data/indus_website/population-script.sql`, Mayig's corpus JSON, the CISI 1 scan (`research/literature/sources/joshi_parpola_1987_cisi1.pdf`, first 431 PDF pages, which the second half repeats) and the CISI 2 scan (`data/raw/2026-10-06-evidence-census/.../cisi2-archive.pdf`), and the split `data/raw/2026-10-12-conjecture-shots/split.json`.

## Part 1: image index

**File records.** Every file gets a SHA-256, pixel size and a parse of its name. Byte-identical files form one hash group. The name is split on `_` into catalogue keys (`^[A-Za-z]{1,6}-\d+$`) and the tokens that follow each key. CISI 1 (printed pp. XXIV–XXV) defines the tokens: an upper-case letter is a side (A obverse, B reverse, C upper, D right, E lower, F left, G for the four-sided prisms M-494 and M-495); the matching lower-case letter is a modern impression of that side; an Arabic numeral after the side numbers separate inscriptions on one side; a numeral in parentheses numbers parts of one side shown in several photographs; `bis`, `ter`, `quater` mark a second, third or fourth photograph of the same side. File names add `imp_` before a lower-case side (impression), a numeral before the side (CISI's parenthesized part numbers, for example `H-275_1_A` captioned "H-275 (1) A"), numbers of 10 or more (the printed scale in per cent, such as `_100_`), `4` or `-` between side letters (caption "B+D" or "B-C", a view across several sides) and free words (`interior`, `duplicate`, `crop`). A name with several keys is a crop that shows several objects, each of which receives a link. Tokens that fit none of these rules are kept as residue and the record is flagged.

**Key normalization.** A key is matched to the Lipi CISI value after trimming whitespace. Where the file prefix differs from every Lipi prefix only by an upper-case `I` written for a lower-case `l` (`DIv`, `BIk`, `DIp`) and the corrected key exists in Lipi, the corrected key is used and the link is flagged `prefix_corrected`. No other fuzzy matching is done.

**Volume and page files.** Files named `vol1_page_N_…`, `vol2_page_N_…`, `z_fix_…` and `fix_vol2_…` carry no key. Their printed caption is read visually from caption-strip contact sheets; a caption read with confidence is recorded as an assignment with the reader's note, and an unreadable or absent caption leaves the file unassigned. The page number in the name is tested against the scans (whether it is the PDF page or the printed page) on at least five files before it is used.

**CISI volume and page for named files.** The CISI 2 text layer and a tesseract reading of the first 431 pages of CISI 1 give, for each PDF page, the printed page number, the running heading (site and catalogue range) and the caption keys. A key is placed on a page when its number falls inside the page heading's range for the matching site prefix, or when its caption is read on that page; disagreements are recorded and the page is left blank. The volume of a key with no page follows the catalogue ranges in `experiments/2026-10-06-evidence-census/synthesis/catalogue-coverage.csv`.

**Face join.** A face is linked to every file whose parsed keys include the face's CISI key. The export gives no side letter for a face, so each link carries a side rule. For an object with one face row the face is presumed to be on side A, CISI's reference side. For an object with several face rows, face `n` (the suffix of the record identifier) is presumed to be on the `n`-th side letter in alphabetical order among the side letters that occur in that object's image names (rule `ordinal`). Each link then gets a relation: `face-side` when the file shows the presumed side, `other-side` when it shows only other sides, `multi-side` when it shows several sides including the presumed one, and `side-unknown` when the name has no side. Each link also gets a kind: `object` for an upper-case side (the seal, tablet or sealing itself), `impression` for a lower-case side or `imp_`, and `mixed` or `unknown` otherwise. Faces without a usable CISI key, and keys with no file, have no link. Nothing is forced: a parse that leaves the key uncertain produces no link.

**Coverage.** Faces and objects with any linked image, with a `face-side` object photograph and with a `face-side` impression, by object type group and by the six main sites plus others, using the inventory's grouping code. The "before" figures are recomputed with the inventory's rule on the same inputs.

**Verification.** A simple random sample (seed `2026-10-13-image-index-and-units`) of 60 face–image links is viewed on contact sheets that show each whole crop with its printed caption. A link is correct for identity when the caption names the linked key, and correct in full when the kind (object or impression, judged from the caption case and the relief) and the side relation also hold; for a `face-side` link the visible text must also be consistent with the face's recorded sign count. A second targeted sample of 20 links from objects with several faces tests the `ordinal` rule, and 15 links from multi-key crops, corrected prefixes and caption-read files test those joins. Precision is reported for each sample with a Wilson 95% interval. A wrong side assignment in the targeted sample requires a revised rule, recorded as an amendment, before the index is reported. The reader is an AI model (Claude Opus 5.5) reading printed halftones.

## Part 2: dimension units audit

**Values.** For each face and axis (horizontal, vertical, thickness) the audit records the Lipi as-recorded field (`h`, `v`, `th`), the Lipi millimetre field (`horizontal(mm)`, `vertical(mm)`, `thickness(mm)`), and, for the same object, the older website export's `WIDTH`, `HEIGHT` and `THICKNESS`. Mayig carries no size field; that is checked and reported. Faces of one object are compared; if they agree the object row holds the value once.

**Unit of record.** An as-recorded string with `cm` or `mm` takes that unit. A plain number takes the unit whose factor (25.4, 10 or 1) brings it to the millimetre field: `exact` when the difference is at most 0.051 mm (rounding of the conversion to 0.1 mm), `rounded` when at most 0.51 mm (rounding to whole millimetres), `approximate` up to 0.6 mm, the inventory's tolerance. A plain number that fits no factor within 0.6 mm is a `mismatch`; its likely cause is assigned by rule (digit transposition or typing slip when one digit differs, unit slip when another factor fits, rounding, or different measurement otherwise). A millimetre value without an as-recorded value has unit of record `mm (not stated)`.

**Precision.** The precision of an as-recorded number is one unit in its last decimal place. For inch values with two decimals, the value is also tested against eighths, sixteenths and thirty-seconds of an inch (within 0.005 in), and the share is compared with the share expected by chance for two-decimal values. Millimetre values without an as-recorded value take the precision of their last decimal (1 mm or 0.1 mm). A millimetre value that is a conversion inherits the precision of the recorded inch value (2.54 mm for 0.1 in, 1.59 mm for 1/16 in). Ranges such as `5 - 9` are kept as minimum and maximum.

**Website export.** The SQL declares the three sizes as `FLOAT` without a unit. Records are joined to Lipi by `SEALID` against `object_family_id` when the CISI keys agree or both are empty, and otherwise by CISI key; the join rule used is recorded per object. Each axis is classed as `equal` (within 0.051 mm), `rounded` (within 0.51), `approximate` (within 0.6), `swapped` (horizontal and vertical exchanged), `inch-valued` (agrees after multiplying by 25.4), `one-side-zero`, or `different`.

**Flags.** Zero in a millimetre field with no as-recorded value (`placeholder-zero`); zero with an as-recorded value (`conversion-missing`); an as-recorded value with no millimetre value (`mm-missing`); a range with a zero lower bound, a reversed range or a malformed string; a millimetre value equal to its inch value (`unconverted`); a plain as-recorded number above 10 that converts as millimetres (`mm-in-inch-field`); markers `(ext)`, `?`, `+?`, `(estimated)`; a face dimension of a seal or tablet under 3 mm or over 150 mm, or any value over 1,000 mm (`implausible`); horizontal and vertical exchanged against the website export (`swapped-axes`).

**Seals in the split.** Shot A's tables are rebuilt by importing its `seal_table.py` and `rank_lib.py` read-only and reading `split.json` directly, as the plate-check package did; nothing is appended to Shot A's confirmation-access log. For each half the audit counts, among all seal families with usable size and among Shot A's size-text population (one seal per component), the seals whose two face dimensions are inch conversions, rounded to 0.1 in, on a sixteenth-inch grid, recorded in millimetres, whole millimetres, or flagged.

## Outputs

Tracked in this package: scripts; `run-2026-10-13/` with the image file records (file name, hash group, parsed fields, volume and page), the face–image links (face and object identifiers, file names, kind, side relation, rule, flags), faces without an image, coverage tables, the verification samples and verdicts, the dimension table (identifiers, numbers, units, precision, provenance, flags), mismatch and disagreement lists, split counts and input hashes. These hold identifiers, numbers and judgements and no sign sequences or images. The dimension values are record-level Lipi metadata, which has no licence; they are outside the project's CC0 dedication, like the attributed metadata of the object ledger. Contact sheets, page renders and OCR text stay local under `data/raw/2026-10-13-image-index-and-units/`. Runs write to new directories and refuse to overwrite.
