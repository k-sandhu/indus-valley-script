# Review of Package O, release 0.3.0

Reviewed 8 October 2026 against the committed folder `experiments/2026-10-08-hf-public-release/` (commit 76a4ac4) and the private Hub repository `ksaw008/indus-reference-benchmarks` at commit `541766d5ea8a4c3b3ec5fcc416ee764af8763afb`. This review leaves `REVIEW.md` and `review/` unchanged and reuses their scripts as adapted copies in [review-0.3.0/](review-0.3.0/).

## Verdict

The 0.3.0 results stand. All 23 configurations load from the Hub and equal the local Parquet files cell for cell (3,308 rows), and the 136 files in `release/` are byte-identical to the Hub copy (the Hub adds only its own `.gitattributes`). The chart table equals package P's `chart-reference-v2.1.json` on every code, class, alternative and confidence, and all 36 changed cells carry previous values and a change note. The flags on reference units and prediction alternatives equal `impact-v2.1.json`. The v3 tables, images and readings equal package M's frozen files, and the staged scorer reproduces the v1, v2 and v3 metrics files with zero mismatches over 4,600 to 6,200 compared values each, including v3 physical-line recall. A fresh build reproduces all 135 generated files byte for byte, and the privacy and rights scans find no private name, local path, Lipi, Mayig or website sequence, or copied third-party prose. The most important problem is in the scoring instructions. The card lists `printed_inscription_id` and `classification_literal` as required prediction fields, but those are reference-side names. The scorer reads `inscription_number` and `classification_code`, so a prediction file written from the card scores 0 correct inscription numbers and 0 correct classifications without any error, in all three benchmarks (with the right names the frozen baseline gives 23 and 19 of 60, 62 and 55 of 80, 71 and 72 of 80). Neither prediction-side name appears anywhere in the release outside the scorer code. The 0.2.0 review missed this because its test file copied field names from the frozen predictions. Three smaller problems follow in the required fixes: reading-table flags that disagree with P's impact file, a `CITATION.cff` licence list that the CFF schema reads as a choice between licences, and a model version stated for v2 readers that package M does not record.

## Method and scope

Counts keep their bases. Row and bootstrap intervals are stated as not clustering by page next to the v3 results, and the 28 numbered v3 rows on eight pages are named. The corrected-label rescoring is deferred. That follows P's own wording, which makes it conditional on resolving 18 v2 and 31 v3 unlocated identities and the sample 58 conflict; v1 has no unresolved identity, so a v1-only rescoring was possible, but it would have mixed vocabularies across the three frames. The card says where the deferral stands and what the flags mean.

The protocol amendment for 0.3.0 is headed "before the new build", but `PROTOCOL.md` was last written at 15:14, after the first 0.3.0 build records (14:51) and validations (14:52 to 14:57), and its later paragraphs record post-build repairs. All of this is in one commit, so I cannot confirm from the files that the first paragraphs preceded the first build. The repairs are labelled as amendments, and none changes a frozen value.

Scope is clean. The card makes no decipherment, sound or meaning claim, labels the chart and the repair references as AI-produced without expert review, and keeps `Exploratory`, `Frozen evaluation`, `Verified computation` and `Failed` apart. The chart status sentence follows P's `adjudication_limit` text. No Lipi, Mayig or website sequence and no museum or book prose is present.

## Required fixes

1. **Prediction field names (high).** In "Score a new row reader", replace `printed_inscription_id` and `classification_literal` with `inscription_number` (a string) and `classification_code` (a five-position string with spaces), explain both in `FIELD-DEFINITIONS.md`, and make `validate_predictions` reject a row that lacks either key (null stays allowed). Then run the card's own minimal example against the baseline summary, as I did in [readme-snippets.json](review-0.3.0/readme-snippets.json): built from the documented fields with the scorer's names, the files reproduce the baseline summary, rows and bootstrap exactly in v1, v2 and v3 (calibration counts 140, 252, 315); built with the card's names, number and classification correct are 0 in all three.
2. **Reading flags (medium).** `benchmark_readings.chart_correction_flags_json` disagrees with `impact-v2.1.json` `public_readings` in two ways. Independent readings never fill `candidate_fields_would_change` (26 units that P lists as definite changes: v1 reader A 6, v1 reader B 5, v2 reader A 15; the code leaves it empty unless the reading is adjudicated), and v2 reader B has 20 corrected-cell units against P's 12, with 7 class-metadata units against 6, because the flags also follow `shape_only_chart_locations`. Fill the field for those readings or state in the field definition that it is populated for adjudicated references only, and state which location fields the flags join. The v3 independent readings have the same empty field and no impact record to compare with.
3. **CFF licence list (medium).** The CFF 1.2.0 schema comment reads a list of licences as OR, so `license: [CC0-1.0, CC-BY-4.0, Unlicense]` tells a machine reader that all content is available under any one of the three. Remove the key, or keep one SPDX value and send readers to `LICENSE` through the `message`, so the per-component structure in the card and `LICENSE` is the only statement.
4. **Reader model attribution (medium).** The card and `REPORT.md` say two Claude Sonnet 5.5 readers and a Claude adjudicator produced "each repair reference". M records "5.5" only for v3; its v2 documents say "Sonnet" without a version, and the release's `reader-metadata.json` carries no model field. State the version for v3 and "Sonnet, version not recorded" for v2.
