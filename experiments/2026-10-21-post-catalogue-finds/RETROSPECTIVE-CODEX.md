# What we delegated to Codex and how it went

We chose the sources, wrote the protocol and its amendment, reviewed every output and decided the uncertain joins in the coordinating session (Claude Opus 5.5, `claude-opus-5-5`, Claude Code desktop app). The Codex CLI (`codex-cli 0.160.1`) running `gpt-6.1-sol` at `model_reasoning_effort=xhigh`, in the `workspace-write` sandbox, did the mechanical work in ten runs. Each run had a complete prompt in this directory stating its owned paths, its invariants (no commits, no edits outside the owned paths, raw material local, inscriptions not transcribed or described), its deliverables, a self-test and the content of its final message, and each was launched detached through Git Bash from a `launch-codex-*.sh` script. Logs and final messages are local under `data/raw/2026-10-21-post-catalogue-finds/codex/`.

## Acquisition

Run 1A called the repository's own `fetch_http` routine from `tools/fetch_data.py` on proposed manifest entries that carried each Internet Archive identifier, byte count, MD5 and SHA1, and recorded the SHA256 at download; all 104 archive MD5 and SHA1 pairs matched. Its one write outside the owned paths was a bytecode cache, `tools/__pycache__/fetch_data.cpython-313.pyc`, created by the first import before it disabled bytecode writing; we deleted it. It found that the ASI mirror's "1996–1997" file is the 1997–98 volume and its "1997–1998" file a byte-identical copy, and fetched 1997–98 from the Internet Archive instead. That left IAR 1996–97 unread, which we noticed while writing this record. The sandbox needed `-c sandbox_workspace_write.network_access=true` for downloads, which a 20-second test run confirmed before launch.

Run 1B found the current ASI publication index, which supplied the six IAR volumes that the October census had failed to fetch (2001–02, 2002–03, 2004–05, 2005–06, 2008–09, 2011–12), and seal studies for Farmana, Bhirrana and Bagasra that list seals one by one. It found no IAR volume after 2013–14. Several downloads were covers, contents pages or landing pages, which it recorded as such; the file registered as Desset 2022 on the Chanhu-daro seals turned out to hold other front matter and an unrelated essay, which run 2P discovered. Run 1B withheld one word from two publication titles because the word names the seals' animal; we kept the withholding, since the full titles are recoverable from their links and our protocol forbids naming a motif in any file.

## Extraction and the disk stop

The four regional extraction runs started together at 04:38. Ten minutes later drive C: fell below 200 MB free, driven mostly by other work on the machine, and we stopped the four processes to avoid failed writes, recorded their Codex session ids and wrote [RESUME-2.md](RESUME-2.md), a continuation prompt asking each run to check for truncated files, download nothing and keep OCR output to text. Before resuming at 05:51, with 11.7 GB free, we re-hashed all 150 downloaded files against their records; none differed. The `codex exec resume` command accepts neither `-s` nor `-C`, so the resume scripts set the sandbox with `-c sandbox_mode="workspace-write"` and run from the repository root.

The extraction prompts asked the runs to read source pages for identity fields only. Runs 2G and 2P reported that their first text filters were too broad and showed them descriptive passages (parts of the Bagasra seal study, pages of the Nuhato report, the Ganweriwala notice and the misfiled Chanhu-daro witness) before they narrowed the filters; both logged the pages in their exposure logs, and no description reached a tracked file. A later test using these objects must treat the `gpt-6.1-sol` runs as exposed for those pages.

Run 2P listed 144 rows, of which 139 are bone and ivory rods from Harappa and Mohenjo-daro in Parpola's 2019 paper that carry CISI numbers and are kept only for audit. Run 2G listed 93 rows for 23 Gujarat and Maharashtra sites.

## Gaps we closed

Two IAR volumes had fallen through. We fetched the Internet Archive copy of IAR 1996–97 with `fetch_data.py`'s `fetch_http` (all three files matched the archive's MD5 and SHA1), found its archive OCR unusable because the item had been read as Devanagari, and tested Tesseract on four pages (about 600 words a page, 70–77% clean) before giving the volume to run 2E. IAR 2003–04 had been held only as the archive's equally unusable OCR; the ASI publication index that run 1B had used lists it as download 115, so we fetched it there (641 pages) for run 2F. The same index's file for Nath's Rakhigarhi report (download 12) turned out to be a two-page cover, as the Dholavira route had for run 1B, so Rakhigarhi rests on the Internet Archive draft, which run 2N found to be dated 31 December 2014 and to lack a seal catalogue. The scripts are in `acquisition-coordinator/` and the records in `manifest-proposals-coordinator.json`.

Runs 2E and 2F each stopped once with the service message "Selected model is at capacity" after their OCR and sweep were saved. Both were resumed in their own sessions with [RESUME-CAPACITY.md](RESUME-CAPACITY.md) and finished without repeating OCR.

## What the extraction runs did well and where they needed checking

The runs found the object-level structure of each source without being told where it was: run 2D located the Dholavira report's seal context tables and narrative catalogue and joined them by catalogue number (203 of 210 rows carry a registration), run 2G used the earlier Kanmer package's witnesses for the chapter 8 registrations, and run 2N discovered that the Internet Archive Rakhigarhi report is a draft and that the held `rakhigarhi_inventory.pdf` is a different work (the Chandigarh Circle inventory of monuments). They also reported totals that disagree with their rows, with pages, instead of forcing agreement.

Three habits needed our attention. Every extraction run reported that an early text filter showed it descriptive source text before it narrowed the filter; they logged the pages, and the README states the resulting exposure. Run 2D dropped unit tokens from Dholavira depth values to pass the content scan, which was written to catch dimensions; the depths stay usable but their unit has to be read from the report. Run 2P was given a download that turned out to be the wrong text, and reported it rather than extracting from it.

## Matching and verification

Run 3 did what its prompt asked and no more: it compared registrations after stripping a site prefix, accepted a registration contained in a longer local value, and treated fields it could not parse as not comparable. Those rules missed every Dholavira `DHR-` registration that the report prints without its prefix, matched `218` to `DHR-21897`, and left the Farmana trench codes unread. We should have written the normaliser and the comparison of trench and grid codes into the prompt; instead we corrected them in the review, which is recorded in `join-decisions.csv`.

Run 4 was the most useful run of the package, because it held us to the frozen protocol. Its first pass found that 67 of our joins rested on find context, which the protocol's rule for `matched` does not accept, and we turned them into protocol candidates with the joins kept as a labelled refinement. Its second pass found candidate sets that still contained local objects whose own context conflicted with the row, and we applied its conflict test to every set; its third pass found none left. It also noticed, while running, that we had revised the list under it, captured each revised input with its hash, and checked both states rather than mixing them. Its blind sample measures how far a reader confined to the cited page can confirm each field, which is a stricter test than we had in mind and explains its low agreement on seasons and findspots. Like the extraction runs, it reports that an early display filter showed it descriptive source text.
