# October 6–7 research program: approach, problems and repairs

On 6 October 2026 the user asked for a wider program after the contribution assessment: stronger machine-learning models for the Paper 001 restoration benchmark, a census of where Indus evidence is indexed and with what metadata, an inventory of project results outside decipherment, the directions proposed by Dennys Frenez in a recorded lecture and by other researchers, a backward chronology from later South Asian scripts, and new analyses of the Indus civilization beyond the script. The user asked that substantive work go to GPT-6.1-Sol through the Codex CLI, token-heavy work to GPT-6-Luna, and checking to Claude Sonnet 5.5, with parallel agents. The program record, prompts and launch scripts are in [the program directory](../../experiments/2026-10-06-research-program/README.md).

## How the work was organized

The coordinating Claude session wrote ten package prompts sharing one instruction file ([COMMON.md](../../experiments/2026-10-06-research-program/COMMON.md)) that carried the repository's evidence, rights and writing rules. Each package owned one experiment directory and one ignored local raw directory, wrote a protocol before outcomes, and proposed its registry entry in its own directory. Codex ran in its `workspace-write` sandbox rooted at the owned directory with network access and live web search; a test write outside the workspace was refused before launch. Package A also had a separate CUDA PyTorch environment outside the repository.

Every finished package went to a Sonnet reviewer with a common checklist ([REVIEW-TEMPLATE.md](../../experiments/2026-10-06-research-program/prompts/REVIEW-TEMPLATE.md)): rerun the stated commands, compare headline numbers with saved fields, open cited sources, check method and scope, and report boundary violations. Reviews were saved as `REVIEW.md` in each package. Required fixes went back to the same Codex session with `codex exec resume`, so the model kept its own context. At the user's request the coordinator committed and pushed at each milestone on the branch `research/2026-10-06-program`, after checking that only code, protocols, reports and aggregates were staged.

## What went wrong and how it was handled

**GPT-6-Luna output was thin or misattributed.** The four packages first assigned to Luna finished in 9–30 minutes. The recommendations survey had 33 rows, of which the first review found 7 supported by their cited sources, 8 attributing recommendations the sources do not contain, and 14 of 31 source records with wrong titles, venues, years, authors or URLs. The first site census left nearly every metadata field unassessed and gave object counts for four of 89 sites. The collection census captured one direct catalogue count. A stricter per-site checklist improved the regional batches only partly: the north India batch ran 33 searches for 24 sites. The coordinator moved every source-citing package to GPT-6.1-Sol, resuming the Luna sessions with the model switched. The rebuilt survey has 59 rows from 28 opened sources, 54 supported and 5 partly supported on full re-check; the collection census confirmed 114 online museum records and joined 61 to corpus records; the regional batches ran 130–247 searches each. Luna also introduced damaged characters (replacement marks for dashes and accents), which the Sol passes repaired.

**The lecture transcript was unavailable to the packages.** Package F's requests were throttled by YouTube. The coordinator opened the video in the desktop app's browser; the transcript panel request returned HTTP 400, and a direct caption fetch returned an empty body. Capturing the caption track the player itself loaded gave 1,166 lines. The coordinator checked the user's summary against it at each timestamp and recorded paraphrased statements in [frenez-talk-check.md](../../experiments/2026-10-06-research-program/frenez-talk-check.md) without saving the transcript. Those statements became follow-up tests for packages D1, D2 and E.

**The disk filled.** About 75 minutes into the parallel runs the system drive reached zero free bytes, and five Codex processes stopped with Windows error 112. The session's own additions were about 17 GB: the PyTorch environment (5.8 GB), its pip download cache (2.7 GB), package raw outputs (7.4 GB, 4.2 GB of them package A's predictions and model files) and run logs. The coordinator purged the pip cache, compressed finished run logs and changed the launch scripts to write compressed logs. Interrupted runs resumed with an instruction to check for truncated files and keep disk use small; package A removed 450 unneeded arrays (2.04 GB). Large unrelated items on the drive, including about 17 GB of earlier Codex session history and several gigabytes of installer and diagnostic files, were reported to the user rather than deleted.

**Editing a running script broke its last lines.** The coordinator edited `resume.sh` while four copies were running. Bash reads a script incrementally, so each copy failed with exit code 2 after its Codex session had finished. Each package's own final message and files confirmed completion. Running scripts should be left unchanged; a new version belongs in a new file.

**Packages read each other's unfinished work.** Package C reported figures from the census packages while they were still running; its review caught this and the figures were removed. Several census files stored long search-result snippets in source title fields; the synthesis package was asked to list them for trimming. Codex could not run `git status` inside the sandbox because Git rejected the repository's ownership, so the coordinator checked boundaries with Git itself before each commit. A crash dump from a Git Bash `grep` appeared once in the repository root and was removed.

## The 7 October continuation

The ledger and digitization packages added three process lessons. Agents running in the same Claude session shared one scratch folder, so helper scripts written by different blind readers overwrote each other; the readings themselves were unaffected, and the adjudicator was given its own temporary folder. GitHub refused every push to the repository for about half an hour with HTTP 500, including an empty test commit, while the repository, credentials and status page were normal; the commits stayed local and went through on a later retry. Packages kept tracking replay copies of large outputs despite instructions, and two outputs exceeded Git limits; those were excluded by rule and backed up, verified, to the private Hugging Face dataset with `hf_host.py`, which also moved package A's 3.09 GB of predictions off the full disk.

## What the reviews changed

The reviews changed several conclusions. The single fitted Dholavira weight unit of 14.003 g turned out to blend weights of 5–100 g (13.716 g) and 1.3–5 g (14.280 g); the western "Indus-standard" counts fell below a chance control. The strict-rule matches in the resemblance pilot dropped under independent recoding and coder agreement was 46%. Package D1's Harappa period comparison is confounded by excavation mound and record source. Package A's audit found that the broader corpus export links 144–159 benchmark training strings per fold to test strings through other faces; the review traced these to sixteen identical one- or two-sign texts and estimated a 0.75–0.84-point effect on Paper 001's Markov results. The backward chronology's 600-year gap at 1300–700 BCE rested on one Pirak row and on omitted dated contexts; with Daimabad Phase V and the other omitted rows added, the broad record has no empty century. The apparent change in seal motifs across Harappa periods came from subphase labels sharing one date range. The census review raised the museum joins to a lower bound of 68 of 114 and found 32 further copied snippet titles. Each package's `REVIEW.md` lists the checks and fixes, and later amendments are labelled Exploratory beside the preserved first endpoints.
