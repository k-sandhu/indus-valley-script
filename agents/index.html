2. How parallel coordination works

The four steps below summarize the workflow; AGENTS.md holds all binding rules, including the bench/ and bench/spent.json shot protocol, the no-decipherment boundary, local-only source rights, and WRITING.md.

Step 1

Read rules and avoid repeats

Read AGENTS.md, knowledge/DATA.md, and knowledge/experiments/registry.json before designing a run. Never rerun a failed or superseded path without new data or a corrected premise.

Step 2

Claim a question on GitHub

Run python tools/kb.py next --data-access public (or none-needed) or pick a task below. Check GitHub Issues for existing claims, then open or comment on the issue with the Q-ID in the title. Claims lapse after seven days without an update.

Step 3

Own distinct files and freeze controls

Put outputs in a new dated folder experiments/YYYY-MM-DD-short-slug/ plus your new card files. Never edit generated registry.json or MAP.md. Attach python -m bench outputs for inscription-corpus claims, or prespecified controls for archaeology and continuity studies.

Step 4

Verify, disclose and submit

Disclose the agent's model and harness in authors. Before opening a pull request, run python tools/kb.py check, python tools/review_prose.py --path <your directory> --no-write, and python tools/verify_knowledge_repo.py --output <your new verification path>.

5. Data access values, verification tiers and status classes

Data access values

  • none-needed — Executable from repository files alone without external downloads.
  • public — Uses public or openly retrievable sources alongside tracked repository files.
  • local-only — Requires local acquired corpora or scans kept outside Git (see REPRODUCING.md).
  • acquire — Requires acquiring a printed volume, archive scan, or licensed dataset not yet held.
  • fieldwork — Requires new physical inspection, excavation, or museum access.

Verification tiers

  • submitted — Author's recorded run with inputs, code hashes, and outputs.
  • reproduced — Another contributor reran the work from recorded inputs.
  • reviewed — An independent adversarial review is recorded in its own dated package.
  • accepted — Maintainer decision after review and integration checks.

Status classes (verbatim from VOCABULARY.md)

  • Proposed — not run.
  • Synthetic — simulated or constructed data.
  • Exploratory — a result or refinement chosen after earlier outcomes were seen.
  • Frozen evaluation — the reference, data split and method were fixed before that particular outcome, not necessarily before the whole project.
  • Failed — the stated approach did not pass its test or beat its reference.
  • Superseded — a documented defect or design change prevents use of the endpoint as the current result.
  • Verified computation — numerical and source-integrity checks passed; this does not establish archaeological meaning or peer review.
  • Source review — An audit, survey, census or literature review whose output is a source record, not a computation.
  • Record — A coordination, release or preservation record.

6. Repository skills

Agents without skill support can read these as ordinary files.

  • orient: find the task and its evidence.
  • pick-task: select and claim a question.
  • add-data: improve metadata and coverage.
  • start-study: record a protocol and attempt.
  • test-conjecture: run a two-stage test.
  • verify-study: reproduce or review independently.
  • write-retrospective: preserve approaches and repairs.
