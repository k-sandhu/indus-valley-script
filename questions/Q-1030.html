Question

Can the project hold one register with a row per physical object, separate tables for faces, images, identifiers, contexts and assertions, and a value_status for every field, populated from all held sources and regenerated by one script?

Why it matters

The owner's first priority is a complete record per object. Today the metadata sits in the Lipi export, two census packages, the object ledger pilot, excavation frames and several study folders, each with its own keys. The target schema in DATA.md defines the fields and their current coverage; this task makes it a working dataset that later enrichment tasks write into and that coverage reports read from.

What is needed

Read DATA.md, the observation model in context-data-plan.md and the object ledger pilot. Start from the pilot's schema version 2 and its validator. Populate from the Lipi export and image index, the older website export, Mayig, the census museum joins and the ledger pilot first; add CISI basic data, excavation tables and chronology mappings as their tasks finish. Keep raw values beside normalized values, record each assertion's source and page, and keep the register under data/ with a tracked schema, build script and coverage report. Release of record-level data waits on Q-1028.

How to decide

Done when the build script regenerates the register from the manifest's sources without manual edits, the validator passes, and the coverage report reproduces this inventory's object-level numbers for the fields it already measured (for example 4,075 objects with a CISI number and 3,598 with at least one dimension). Any difference must be explained by a recorded rule change.

Prior attempts

The object ledger pilot built two 200-carrier ledgers with 6,991 and 7,004 assertions; the dataset landscape specified the register without building it.
