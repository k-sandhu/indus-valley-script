# Route test: can a newcomer work from AGENTS.md alone?

15 October 2026. Contributor: Claude Code (Claude Opus 5.5) in the Claude desktop app, working in a fresh Git worktree at commit `0c23046d`, which includes the 15 October process fixes ([maintenance/2026-10-15-process-fixes/](../2026-10-15-process-fixes/README.md)). Status class `record`. This is the test that the [12 October restructure retrospective](../2026-10-12-repo-restructure/RETROSPECTIVE.md) proposed in its last paragraph and that reports A and B of the [14 October review](../2026-10-14-muse-review/README.md) both recommended.

## Result

Both tasks reached a submission-ready state, but only because the session could read the maintainer's local data and could recognise one failing check as inherited. The route from AGENTS.md to a card and its package works: `kb.py next`, `kb.py show` and the cards' prior-attempt links led to the right material within minutes. It breaks in four places. `python tools/kb.py check` fails on every clean checkout, because an attempt card cites a log file that `.gitignore` excludes; the 15 October record of a passing check was measured on the maintainer's disk. Every Priority 1 starter metadata question needs local-only data, and nothing on the route from AGENTS.md says how to obtain it. The claim route sends contributors to GitHub issues that do not exist. The reproduction route gives no path from a finding card to the command that produced it, and the original code writes over its own frozen endpoint. The 28 obstacles below give each location and a proposed fix; [PROPOSED-EDITS.md](PROPOSED-EDITS.md) gives replacement text for the shared files.

The two tasks produced:

- Task 1, metadata: [Q-0009](../../knowledge/questions/Q-0009-distinguish-missing-motif-from-no-motif.md), chosen from `python tools/kb.py next --kind metadata`. The package [2026-10-15-route-test-metadata](../../experiments/2026-10-15-route-test-metadata/README.md) holds the protocol (hashed before any photograph was viewed), a fixed sample of 38 seal faces read against their CISI crops, a versioned label mapping, the coverage change, proposed DATA.md, manifest and card text, the claim text and the registry entry [ATTEMPT-0001](../../knowledge/registry/attempts/ATTEMPT-0001.json). The data result: in the Lipi export, `None` in the motif field means "no motif" on rectangular seals (8 of 8) but not on square seals, where half the sampled faces are too broken or worn to show one. Seal motif coverage falls from 94.2% to 89.9%.
- Task 2, reproduction: [F-0027](../../knowledge/findings/F-0027-long-seal-texts-do-not-repeat.md), "Long seal texts do not repeat". [reproduce-f0027](reproduce-f0027/README.md) rebuilds the population from the protocol's text in a new directory. It matches the frozen counts at every length, with 445 seals of six or more signs and no identical pair. An exploratory widening to multi-line faces finds one pair, C-53 and C-58 from Chanhu-daro, outside the finding's stated scope.

`python tools/kb.py check` with this package and the metadata package in place reports one error, the inherited one in obstacle 19, and two maintainer notes for generated files. With that one ignored file copied in from the maintainer's checkout, it passes ([checks.md](checks.md)).

## How the route was followed

The session read AGENTS.md, then README.md, knowledge/INDEX.md, knowledge/editorial/WRITING.md and CONTRIBUTING.md, as AGENTS.md line 10 and line 16 require, then MAP.md and the skills named in the AGENTS.md table (orient, pick-task, add-data, start-study, verify-study, write-retrospective). For task 1 it ran `kb.py next --kind metadata` with each difficulty and data-access filter, read the five Priority 1 starter cards, checked the issues with `gh issue list`, and read the prior attempts with `kb.py show`. The rule under test was not linked from the card; it turned up by searching for the word "placeholder". For data it tried `tools/fetch_data.py`, then read the maintainer's existing local files and recorded their hashes. It copied the coverage-record format from the 13 October CISI 2 pilot after finding no named format in the instructions. For task 2 it went from the AGENTS.md "Verify or review" row to REPRODUCING.md and the verify-study skill, then from the finding card to its package's REPORT.md and PROTOCOL.md, where the population rule and the code location are. Each step that needed knowledge the route did not supply is an obstacle below.

Line numbers refer to commit `0c23046d`.

## What the route already does well

The layered route held: from AGENTS.md, two commands found a suitable card and its prior attempts, and a card led to a package whose protocol and report were enough to rebuild the result. The data inventory's protocol, the face-image index of 13 October and the CISI 2 pilot's coverage-record files were the three pieces of earlier work that made the metadata task possible in one session. `fetch_data.py --dry-run` showed exactly what a fetch would do before it did it.

## Boldest reading and the test that decides it

The route works for a contributor on the maintainer's machine and fails for anyone else. Two of the four breaks, the failing check and the inputs with no fetch instruction, come from the gap between a clean clone and the maintainer's disk, and so does the verifier's list of 207 inherited errors that hides a contributor's own. The third, the missing issues, blocks claiming for everyone; the fourth, the missing link from a finding to its command, slowed the reproduction without stopping it. The remaining obstacles cost reading time but did not block either task. The deciding test is a second route test after the fixes in [PROPOSED-EDITS.md](PROPOSED-EDITS.md), run by a different model from a fresh `git clone` of the public repository on a machine without the project's `data/`. It passes if that contributor submits a metadata package and a reproduction with a passing `kb.py check` and without asking the maintainer anything.
